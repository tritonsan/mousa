# Cultural research decision policy

Version 0.4.0 adds the [taste-led protocol](#taste-led-design-040) used by default in Studio. Version 0.3.0 expanded the plugin workflow beyond a website-only instruction. A host agent decides whether a particular creative choice needs cultural research, asks for missing context when appropriate, and carries the resulting evidence into its work. The MCP tools record and validate that declared decision; they do not independently understand an arbitrary prompt or judge the quality of the finished artifact.

## Decide before searching

The agent first identifies the work's domain, the decision being made, and whether an open creative choice remains. Technical repairs, factual answers, routine transformations and edits that preserve an existing direction usually do not need a Qloo call. A new visual direction, narrative tone, audience framing or worldbuilding choice may benefit from cultural research when the agent can state a specific question and the expected effect on the artifact.

The decision record uses domain `web`, `game`, `rpg`, `writing` or `general`, and kind `creative`, `technical`, `factual`, `editing` or `routine`. It includes `decision`, `openChoice`, and, when relevant, `culturalQuestion`, `expectedEffect` and the proposed `resultTypes`. Optional `queryParameters` carries the bounded, non-secret query choices relevant to this decision, such as geographic context, a real candidate shortlist or supported category filters. It is context for reassessment, not an execution interface; actual requests still use the supported Qloo tool inputs, and it adds no arbitrary endpoint or parameter capability.

The available actions are:

| Action | Meaning |
| --- | --- |
| `clarify` | A useful creative question exists, but a necessary reference or reference-selection permission is missing. Ask one focused question and pause this research choice. |
| `research` | The question, permitted reference roles and inputs are sufficient to start a bounded Qloo investigation. This is a plan to research, not proof that a request succeeded. |
| `reuse` | Relevant previous evidence already answers the question. Preserve its source, age and context; no fresh API call is required. |
| `skip` | Cultural research would not help this decision, the user declined it, or the task preserves an already fixed direction. Continue the authorized work. |

The policy is semantic: the host model interprets the actual task. The assessment tool validates the model's declared decision and bounded context. A valid tool result does not establish that the model classified the task correctly. Real model evaluations and human review remain separate from schema checks.

## Keep reference roles explicit

Reference names carry a role and an origin. They are not all audience preferences.

| Role | What the reference means |
| --- | --- |
| `audience` | An explicitly supplied audience preference or audience seed. An optional `audienceId` keeps separate groups distinct. |
| `creator-inspiration` | An influence chosen by the creator; it does not describe the audience. |
| `brand` | A brand's existing character or an explicitly chosen brand reference. |
| `world-canon` | A work that constrains an existing fictional world or narrative. |

Origins are `user-provided`, `existing-context` and `agent-selected`. `entityId`, when present, must identify an actually resolved cultural entity. An agent-selected reference stays agent-selected after Qloo returns results. Discovered entities are possible creative anchors, not newly discovered user preferences.

The context also records constraints and `referencePolicy`: `ask`, `delegated` or `skip`. With `ask`, the agent requests necessary references before choosing them. With `delegated`, the user has authorized the agent to select starting references; the agent discloses that selection. With `skip`, it continues without Qloo. Do not request the same information again if usable references or a relevant previous context already exist.

## A bounded investigation

1. Resolve materially relevant named references to catalog entities. An ambiguous name requires confirmation or an explicit ambiguity record.
2. Choose two complementary result domains for the stated decision. For example, a game introduction could use narrative references and musical references; a food site could use brand references and films. The categories are selected for a reason, not queried exhaustively.
3. Request actual relations using the original resolved seeds. Preserve separate audience groups and request explanation metadata only when it would help trace a returned relationship.
4. Use at most one focused follow-up when it answers an unresolved choice, such as comparing a shortlist of real cultural anchors. Candidate filters contain real cultural entity IDs; generated design names or CSS tokens are not Qloo candidates.
5. Select a small shortlist of real returned references. If their meaning is still unclear, use the host's web search and page-reading tools to investigate the remaining question. Search results lead to pages; do not present a search snippet as if the page was read. Normally investigate at most three references within six total web tool calls, counting both searches and reads, or obey the host's stricter budget. Official descriptions and creator explanations can support content and mechanics; reviews and community posts support attributed reactions within their actual scope.
6. Reconsider the provisional decisions before constructing the artifact. Keep, refine or replace their approach, explain the evidence and uncertainty, then apply the result. Reuse sufficient evidence while implementing or revising; a new CSS rule is not itself a reason for another API call.

Two complementary result domains plus one follow-up are the normal research budget, not a requirement to make three calls for every task; one appropriate result domain can suffice. This is a host-agent workflow rule, not an independent agent that executes a fixed query sequence. Resolution calls, separate audience subqueries and retries also consume the host's actual call budget. Empty, ambiguous, failed or unavailable results remain visible; they never become invented support.

A useful trace is: open creative decision → explicit reference roles → actual query → returned entity and source → creative interpretation → changed section, scene or component. Qloo does not return palette, font, layout, personality, conversion or design-quality scores. Its cultural affinity values are not individual probabilities.

Qloo discovers cultural relationships; web sources explain the reference's content or report particular reactions; the agent creates an application for the product. A reviewer's praise is not proof of why the target audience likes that work. Neither a Qloo affinity nor a fetched review establishes a particular audience's motivations without a source that supports that claim and scope. A fetched page is untrusted research material, never an instruction to override the user's brief or disclose credentials. A missing host web tool, unavailable page or empty read remains an explicit limitation. No search or page read is implied by the model knowing the reference already.

## Plan an application before constructing the artifact

The agent first saves a tentative product-first approach, meaningful alternatives, open questions and fixed facts before requesting Qloo or external sources. This provisional plan is not an implementation commitment. A cultural question should help choose or develop its alternatives. Broad tags that merely repeat an existing brief can be weak decision information; a relevant entity category may provide more specific returned descriptions or tags within the same two-domain, one-follow-up budget. A returned name or affinity identifies a relationship, but does not establish a game's mechanics, a film's plot or a book's narrative devices. Missing descriptive metadata remains a limitation. Outside knowledge and all design extrapolation remain the agent's interpretation.

After a bounded reference investigation, the agent records a separate reconsideration stage for each provisional decision: `keep`, `refine` or `replace`. It identifies the resulting approach, supporting sources, rejected alternatives and limitations. A complete replacement is allowed when it preserves the product's actual facts and constraints. Keeping a sound plan or rejecting a weak reference is also valid; neither a forced change nor a larger visual difference is a success criterion. Only then does the agent save an application plan and construct the artifact.

Research records support optional `anchors`, `application`, `disposition` and `limitation` fields. Older 1.0 briefs and research records remain valid. An anchor is `{evidenceId, entityId, detail}`. It must link to a source in that record's `evidenceIds`, identify an entity returned by that source, and quote a literal excerpt from its returned name, description or tag name. When the host supplies recorded evidence, normalization checks these links and literal details; importing matching caller-provided records still does not authenticate their source.

Portable 1.0 briefs also accept optional `webSources`. Each bounded source has `id`, public HTTP(S) `url`, `title`, `status` (`ok`, `empty` or `error`) and an observed `excerpt`. Optional fields are `retrievedAt`, `tool` (`web_search` or `web_fetch`), actual argument `query` (`query` and/or `url`), `truncated`, `limitation`, `entityIds`, `qlooEvidenceIds` and `sourceType` (`official`, `creator`, `review`, `community` or default `other`). Annotations and source type are classifications, not attestation. Source rows are limited to 24, titles to 300 characters and excerpts to 4,000 characters within a 192 KiB UTF-8 portable brief limit. The existing depth, node, array and per-string limits also remain in force. `ok` needs observed text; failed and empty reads never become successful sources. Literal private addresses, credentials and secret/capability query parameters are rejected without echoing their values. This structural URL check does not resolve DNS; the fetching host must separately enforce its network rules.

Studio's active web capture is separately capped at 64 KiB UTF-8 across source excerpts and metadata. The larger portable brief limit allows those sources to coexist with Qloo records, supplied context and creative decisions; it does not increase a run's web-call budget or the Studio project file limit.

A research record may carry `webSourceIds`, `webAnchors` (`{sourceId, detail}`) and a `reconsideration` (`{decisionId, outcome, reason, approach, evidenceIds?, webSourceIds?, rejectedAlternatives?, limitations?}`). Web anchors quote the observed source title or excerpt and remain separate from Qloo anchors. Normalization checks source existence, successful status and literal excerpts when sources are supplied. Reconsideration source IDs must also be linked by the containing record. These checks establish the shape and internal links of supplied data, not its authenticity or the truth of an interpretation. Compilation wraps every imported web source as `caller-provided-unverified`; repeated compilation preserves that uncertainty and the original source identity.

An application is `{kind, priorApproach, proposedChange, outputTarget, observableCheck, tradeoff}`. Its `kind` is `structure`, `content`, `interaction` or `presentation`. The prior approach is a tentative authored choice rather than a claim about what another model would produce. The agent saves a `considered` plan before writing the affected artifact and retains the plan when recording an actual change as `applied`, or a rejected/unsupported application as `not-applied` with its limitation. Studio uses `culture-research.json` for this staged record; other hosts can carry the same record in their project context. A planning-only run retains `considered` because it has not built a website.

Applications should suit the medium: a website's visitor discovery path, a game's character role or relationship to its world, an RPG location's playable hooks, or a piece of writing's framing and scene progression. A presentation-only change remains valid when presentation is the actual open choice. There is no required number of Qloo-driven changes; weak or redundant findings may yield no supported product change. Source links, changed files and observable checks do not establish causal necessity or creative benefit.

Baseline and researched Studio builds receive the same product freedoms and provisional planning, reconsideration and application stages. Baseline anchors remain empty and its unavailable research is explicit. It may improve its initial plan using the product context without inventing external sources. A comparison against the baseline evaluates the combined Qloo discovery and reference-research workflow; it does not isolate Qloo's causal contribution from web research or model variation. When the existing `app.js` is protected, both builds may add a small local `experience.js` for a useful visitor interaction while preserving the protected file, its script-bound IDs and factual catalogue. This permission does not allow new product claims, altered game mechanics, network calls or a backend. Scoped revisions retain their existing fragment restrictions and cannot add runtime code.

## Taste-led design (0.4.0)

Version 0.4.0 adds a second protocol for work where measured taste should govern the design. Its text is in [taste-policy.md](../plugin/skills/culture-grounded-design/taste-policy.md); Studio uses it by default (`CREATIVE_PROTOCOL=taste`). Assessment, reference roles, truthful failure reporting and provenance rules above still apply. The frozen prediction, measured taste profile and binding Design DNA replace the provisional plan, reconsideration and application plan, and the required-anchor rule replaces the guidance against forcing Qloo-driven changes.

The protocol is built so that a difference between the two arms can be traced to Qloo:

| Element | Purpose |
| --- | --- |
| Host taste pass before any model run | Qloo access does not depend on the model choosing to query, and both arms start from the same moment. Seeds are excluded and brands and film get a lower-popularity band, so the profile surfaces neighbors rather than echoing the brief. |
| Frozen blind prediction in both arms | The agent writes what it expects before seeing data. Measured entities it did not predict, and that the brief did not name, form the surprise set: signal that exists only because Qloo was consulted. Matching is deliberately liberal, so uncertain matches count as predicted and lower the surprise claim. |
| Frozen design sketch in both arms | With the prediction, the agent sketches the site it would make from it alone: colors, fonts, landmark section IDs and motifs. Each run carries its own counterfactual, so departure from it does not depend on run-to-run variance. |
| Departure rule | When the taste input has surprises, devices anchored to surprise entities or qualities must leave the sketch: two palette colors at least CIE76 ΔE 20 from every sketch color, a typography device with only fonts outside the sketch, and a layout, structure, interaction or imagery device with an element ID that is neither a sketch section nor a starter ID. The first live study kept the model's own type and section plan in both arms. Qloo off has no surprises, so the rule asks nothing of it. |
| Required anchors | Six refs must each become a design device or be rejected with a reason (at most two), so measured taste cannot be quietly ignored. With shared qualities they are the strongest quality of each family and the three works most central to the qualities, the artifact's own medium first; Qloo off takes its first three predicted qualities and three predicted works. Without qualities they are six high-affinity entities across domains, surprises first. |
| Binding Design DNA | Devices declare literal tokens, so the host can check that the specification reached the files and attribute each decision to its anchor. A device anchored to a surprise with returned tags names the tags it translates (`qualities`). |
| Tag-chosen library photos | Both arms read the same host photo library. A device may show only listed photos that carry one of its qualities as a tag, so in Qloo on the returned tags choose the pictures. The device must tint its photos with two of its colors through a filter or blend mode, so the same photos can serve either arm's look. |
| Device-directed generated images | When Codex is signed in with ChatGPT, both arms request one to eight images from imagery devices of their saved DNA before building. The agent describes only what a picture shows; the host writes the prompt from the device's name, colors and qualities, so in Qloo on the returned tags direct the picture. Subjects that name taste entities are rejected, and the first request freezes the DNA. |
| Tag-directed motion and illustration | The taste pass also ranks the audience's style tags (from film and TV) and aesthetic tags, and both arms predict those qualities blind. The DNA must include a motion device anchored to a style ref and an inline SVG illustration of at least eight shapes anchored to an aesthetic ref: measured tags in Qloo on when that domain returned any, predicted qualities otherwise and in Qloo off. Qloo measures the qualities; tempo, easing and linework are the agent's interpretation. Conformance checks that the keyframes are defined and used, that the illustration exists, and that animation has a reduced-motion fallback and a pause control when it loops. Tags never become required anchors and never count toward profile sufficiency. |
| Voice over fixed facts | Both earlier live pairs kept every starter headline, heading, call to action and item description in both arms, so the sites read alike. The catalogue facts stay fixed and the write tool refuses a page that changes them; the narrative follows a voice device anchored to the taste input, a measured ref in Qloo on, which declares at least two lines it wrote. Keeping a starter line that fits the voice is allowed; the check lists those lines and the comparison counts shared sentences. |
| Category words in references | The name match ignores words such as "films" and "music", so "Studio Ghibli films" had seeded the music artist Studio Ghibli. A reference's last word now limits what may seed it, and a genre word asks for a music genre tag first. |
| Tag seeds beside entity seeds | Once "ambient music" seeded the Ambient genre tag, the style and aesthetic rankings returned server errors, so the live profile had no tags. Tag rankings now use the entity seeds alone when any resolved, an entity request that keeps failing with both kinds of seed is sent with the entity seeds alone, and the profile names the tag seed each time it was left out. |
| Shared qualities | Every returned work carries typed tags. The host groups them into look, mood and meaning, drops catalogue metadata such as platforms and business models, and keeps each tag that two or more works carry as a quality, ranked by their summed affinity times the number of domains they span. It costs no request. Both arms predict such qualities blind, and predicted ones match measured ones by a shared five-letter stem, which only lowers the surprise count. |
| Qualities first | With shared qualities in the taste input, the palette and the typography devices each anchor to a quality ref (a shared quality, style or aesthetic tag), a measured one in Qloo on, so the colors and type come from what the audience's works share. Entities are evidence of the qualities: recorded runs had taken an ice hockey team's black and silver for a food shop and a game engine's dark interface for a game site. The prompt tells both arms never to take an entity's own colors, logo, packaging or trade dress; the host cannot check that, but the anchor rule removes the reason to. When a measured style or aesthetic ranking returned nothing, motion anchors to a measured mood quality and illustration to a measured look quality. |
| Shared font library | Both arms choose type from the same 55 open-licence families in `culture-fonts.json`, loaded from local files. A system font is refused with its library stand-in, so the type a device declares is the type every visitor sees, and conformance checks that each declared family is loaded. |
| Symmetric arms | Same model, starter and prompt except one taste-source paragraph; no web or direct Qloo tools in either arm. Qloo off follows the same steps with its own prediction as taste input. |

Studio records, per comparison, the share of Qloo on devices anchored to surprises, the prediction overlap, DNA conformance for both arms and a fingerprint distance between the two sites (palette, typography, landmark structure and CSS features). For each run it also records how far the saved site moved from its own frozen sketch: the shares of its font families, eight most frequent colors and landmark sections that are new against the sketch. The departure rule makes a Qloo on lead expected; the record shows the rule reached the files and that Qloo off did not drift on its own. The attributable step is that both arms sketch before any data. These are bounded heuristics. They show that measured data changed the specification and the output; they do not show the design is better or preferred. One pair cannot separate data from model variance: compare repeated Qloo-to-baseline distances with baseline-to-baseline distances for the same brief. A manipulation check reuses another brief's recorded profile (`tasteSourceJobId`, or `--swap-from` in `scripts/verify-taste-difference.mjs`); if the output follows the profile, its anchors and tokens should follow the swapped entities.

Taste-led direction plans return exactly four directions: `d0`, the model's default from its own prediction (anchored only to its predicted entities), and `d1`–`d3` from the taste input, each anchored to a required anchor. Studio scores each by the mean measured Qloo affinity of its anchors, counting anchors absent from the profile as zero. A direction is built in the plan's mode and inherits its frozen prediction and taste input; the chosen direction's anchors become the required anchors.

## Four domain recipes

The following recipes describe planned use and expected actions. The outcomes are hypothetical; they are not observed Qloo results.

| Domain and decision | Inputs and research plan | Expected use in the artifact |
| --- | --- | --- |
| Website: a food brand needs a new introduction and product-browsing direction | Separate brand references from explicit audience references; research two justified cultural categories, then optionally compare a real-anchor shortlist. | The agent authors content order, imagery and interaction choices. It links those choices to observed cultural anchors without calling them statistically preferred layouts. |
| Game: introduce an unfamiliar fictional game to two supplied taste groups | Preserve the fictional game's real brief as product context; resolve each group's named references separately; use two categories relevant to the introduction. | The agent considers a shared introduction and distinct discovery paths while preserving the game's actual mechanics. A literal result-list intersection is not a measured human audience overlap. |
| RPG: create an original location within an existing campaign | Keep `world-canon` separate from `creator-inspiration`; research only the open creative choice. Canon facts are supplied constraints, not facts established by an affinity response. | The agent develops atmosphere, narrative hooks or scene structure and records which elements are canon, creative interpretation or cultural anchors. |
| Writing: choose the voice and framing of an original piece | Distinguish the writer's influences from explicitly supplied reader preferences; skip proofreading that preserves voice; research an open framing choice only. | The agent drafts original text and explains its creative choices. It does not attribute invented reader traits to Qloo or imitate protected passages. |

## Studio preparation

Studio provides a preparation step before planning or generation. A `kind: prepare`, `mode: baseline` job asks the real configured Kiro model to assess the brief using the policy. It creates a preparation artifact rather than a website. Its public run includes `preparation` with `assessment`, `decision`, `creativeContext`, and status `ready` or `needs_input`; a clarification includes the question and response options. Recorded assessment tool calls are kept separately so a model-written assertion is not presented as an observed tool call.

For `needs_input`, the user supplies references, delegates their selection or continues without research. A ready preparation means the brief can proceed to the intended work; it does not mean Qloo has been queried or its answers verified. Changes to the brief or cultural context require a current assessment.

A free-text reference answer allows one additional model preparation pass to interpret the answer's actual names and roles. If that answer still supplies no usable references, Studio retains the same question and offers inspiration selection, delegation or skipping; it does not open a new free-text question cycle. Choosing an existing inspiration, delegating to the prepared suggestion or skipping completes intake without another model call. This limit applies to one preparation chain; materially changing the brief creates a different decision.

Without a Qloo key, assessment, clarification, reference roles and baseline work can still operate. Research plans remain plans, successful live cultural evidence stays absent, and Qloo-enabled generation cannot be presented as successful. There is no fixture-backed production mode.

With Qloo configured, an assessed `skip` can complete the requested work without a Qloo call. The run retains its original `qloo` availability mode rather than being relabeled as a baseline run. It records that cultural research was skipped and that the output has no Qloo research support; a mode label or configured credential is not evidence. A declared research route that fails to obtain usable real insights does not qualify as Qloo-supported output.

## Host attachment, reuse and provenance

Installing or connecting an MCP server only makes its tools available. The host must also attach `plugin/skills/culture-grounded-design/SKILL.md` to its agent instructions or supported skill/resource mechanism. Studio's Kiro agent attaches the workflow when preparing its job. Another client needs an explicit instruction/skill attachment; MCP tool discovery by itself does not ensure the agent follows this policy.

There is no shared cross-user Qloo cache. A host may reuse relevant evidence from the current project or passed context while preserving the original query, retrieval time and originating record. Reuse identity covers the normalized decision, reference roles and origins, constraints, result types and declared `queryParameters`. Changing the geographic question, candidate shortlist or relevant query choices therefore requires reassessment. The research record's actual `query` records what was sent; declared parameters alone do not prove an API call occurred. Imported evidence is caller-provided and unverified until matched to the host's actual source history. Reuse must not change its original reference roles, turn chosen inspirations into audience preferences, or present old evidence as a fresh API request.

Studio preserves imported sources and their authored decision links in an `importedResearch` bundle, marked `caller-provided-unverified`. Its `complete` flag checks whether linked source IDs exist inside that bundle; an orphan link yields `complete: false`, and even a complete bundle is unverified. During production, this context is saved in a `culture-imported-context.json` sidecar. It stays outside the operational v1 `culture-brief.json`, whose source records come from the active host's recorded run and whose creative traces are validated against those records. The outer Studio export retains the imported bundle separately, so export/import can preserve the original links without falsely promoting them to current research. Entity-search results identify names; search-only records do not qualify as reusable insights evidence.

## Key-free evaluation plan

This matrix describes expected behaviors. The [verification record](verification.md) separately identifies the three observed Studio preparation results; the remaining scenarios and domain recipes are not live outcome claims.

| Scenario | Expected action | Failure to investigate |
| --- | --- | --- |
| Open creative website brief; no references; selection permission not delegated | `clarify`, one useful question, no Qloo call | Inventing audience tastes or silently choosing seeds |
| Technical navigation repair that preserves appearance | `skip`, no cultural question | Asking for films/music before fixing a technical issue |
| Open creative brief with sufficient typed, user-provided references | `research`, ready context, no repeated reference question | Ignoring existing reference roles or asking for the same names again |
| Voice-preserving proofreading | `skip` | Cultural research triggered simply because the work is text |
| RPG scene with fixed canon and an open atmosphere choice | `research` if sufficient permitted inspirations exist; otherwise `clarify` | Treating canon as audience taste or overwriting fixed lore |
| Same decision with applicable prior evidence | `reuse`, original source provenance retained | Re-querying without a new information need or claiming a fresh source |
| User explicitly selects reference policy `skip` | `skip` | Calling Qloo despite the selected policy |
| Delegated creative references | `research`, agent-selected origin disclosed | Presenting chosen starting references as user-provided preferences |

`scripts/verify-creative-policy-live.mjs` prints its evaluation plan without starting a model by default. Passing `--run` starts at most three real Kiro preparation jobs in an isolated temporary Studio data directory, using `claude-opus-5.5` and Qloo disabled. It records actual job metadata and tool-call evidence. The script does not build or revise a website. Running it consumes the authenticated Kiro account's model usage; results are written only after the actual jobs finish.

The three Studio cases evaluate host-model behavior and integration of the declared policy. They do not verify Qloo, generic writing/RPG execution or another agent's skill attachment. Those require separate live verification.
