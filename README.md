# Moûsa

Moûsa connects Qloo's cultural data to creative agents through a portable MCP plugin and a Kiro-powered web demo. The product has two parts: `plugin/` carries a creative-research policy and tools for compatible MCP clients; Moûsa Studio lets reviewers prepare a brief and generate designs from the same starter website with Qloo enabled or disabled, and design a playable game character the same way.

All product-facing interface text, starter websites, generated designs, creative directions, decision notes, and reviewer materials use English for the global hackathon. The conversation language does not change the artifact language.

## Implemented scope

- Six starter websites: local food, indie game, boutique hotel, record shop, clothing brand, and creative workshop.
- Background generation through the real Kiro CLI, without simulated model or Qloo results.
- Two independent runs using the same brief, model, and starter files.
- Qloo entity-search and insights tools called directly by the model.
- A preparation step that uses the real model to assess whether a decision needs research, existing evidence, clarification or no cultural work. Reference roles distinguish audience preferences, creator inspiration, brand context and fictional canon.
- Saved workspaces containing the product brief, brand notes, protected files and text, and up to three separate audience groups. JSON context can be imported and exported.
- A choice of two or three model-generated creative directions, followed by a separate website variant for the selected audience. Directions include concrete section changes and tradeoffs; Qloo references are checked against recorded entity and evidence IDs.
- Selection of a section with a unique ID in the working preview, with inspection of its decision notes, source records, and actual file and line changes.
- Scoped revision of one `#id`: the model proposes an HTML fragment and section-specific CSS, which the server validates before applying. The source variant is preserved, and selection can be reverted between completed variants.
- Job-scoped file tools, without general terminal or filesystem access among the model's tools.
- HTML/CSS/JavaScript previews on a separate origin, generation progress, source data, and model decision notes.
- STDIO MCP and token-protected stateless HTTP MCP (`POST /mcp`).
- A photo library for the local food starter: 21 CC0 and public-domain product photographs that taste-led designs may show (see [Photo library](#photo-library)).
- Generated images through Codex when it is signed in with ChatGPT: a DNA imagery device requests them and the host writes every prompt (see [Generated images](#generated-images)).
- A font library of 33 open-licence (SIL OFL 1.1) families served with every site, and motion and SVG illustration devices directed by Qloo's style and aesthetic tags (see [Fonts, motion and illustration](#fonts-motion-and-illustration)).
- Shared qualities: the look, mood and meaning tags that the audience's measured works have in common, which set the palette and type in place of any single entity's own look (see [Shared qualities](#shared-qualities)).
- A Game character tab: one playable character and the look and music of its moment, in an RPG scene whose lore and layout are fixed, designed with and without Qloo from the same brief and played side by side (see [Game character](#game-character)). Codex can paint each character as finished game art on its own rig (see [Painted characters](#painted-characters)).
- Production stages in websites, the game character and any project the plugin opens: each designer reads its taste input, plans how every DNA device is made from the methods the host offers, and reviews captures of what it built (see [Universal production protocol](#universal-production-protocol)).

Without a Qloo key, the starter websites, creative preparation and baseline generation through the existing Kiro session remain available. A Qloo research route requires usable real insights. If a configured Qloo run correctly skips research, the requested work can complete without API calls; its availability mode remains recorded, while its output explicitly has no Qloo research support. This release does not claim automatic cultural correctness or improved conversion. Model decision notes are creative interpretation; Qloo data is recorded separately.

Creative work now records an application plan before construction: a tentative approach, literal returned source details, an authored interpretation, the proposed output change and a visitor check. Both baseline and Qloo runs can add useful local interactions while keeping protected files intact. Studio's Design decisions tab shows these traces and server-owned checks for plan timing, existing targets and actual changes. Older records remain readable with explicit missing application detail. These checks establish implementation and provenance; they do not prove that Qloo was necessary or that the design is better.

The [Echo Atlas audit](output/qloo-difference-audit/audit.md) explains why broad mood tags and post-hoc source links did not demonstrate additional value in the earlier comparison. The [application verification harness](scripts/verify-research-application-live.mjs) prints its plan by default; `--run` starts one shared preparation and two real model runs from the same game brief. `--verify-job=ID` checks an existing local comparison without model or Qloo calls. Weak or unused evidence remains a valid observed outcome, rather than a reason to force decorative differences.

Brand protections check that protected files remain unchanged and that specified text appears the same number of times. They do not automatically measure a brand's visual or semantic integrity. This release works with six static starters; it does not include a general repository importer.

## Taste-led protocol — 0.4.0 (default)

In 0.3.0 both arms had the same web tools and the Qloo arm queried Qloo on its own initiative. It often re-found what the model already knew, so the two designs differed little and the difference was hard to attribute. With `CREATIVE_PROTOCOL=taste` (the default), Studio builds and plans follow a fixed sequence:

1. **Host taste pass (Qloo on only).** Before any model run, Studio resolves the brief's audience references (entity search, then tag search, with strict name matching) and requests cross-domain neighbors for brands, film, music, books and TV, plus games, destinations or places when the starter or audience calls for them. It also requests the audience's top style tags (the pacing and look of the films and TV it likes) and aesthetic tags. Seeds are excluded from the entity results, and brands and film get an extra lower-popularity band. A same-named work wins over a place ("Paterson" the film, not the city). A category word at the end of a reference decides what may seed it: "Studio Ghibli films" accepts only films or their makers, so the music artist Studio Ghibli is reported instead of used, and "ambient music" asks for the Ambient genre tag before any artist. When an entity also resolved, a tag seed stays out of the style and aesthetic rankings, which Qloo answered with server errors once a genre tag joined them. Requests run two at a time, and a request that hits a rate limit, a timeout or a server error is retried; an entity request that times out or gets a server error twice with both kinds of seed is sent once more with the entity seeds alone. The pass makes at most 24 requests. Unresolved names are reported, never replaced; if nothing resolves, the comparison stops before any paid model run. Without another request, the host then reads the typed tags on the returned works, groups them into look, mood and meaning, leaves out catalogue metadata such as platforms, and keeps each tag that two or more works carry as a [shared quality](#shared-qualities).
2. **Blind prediction and sketch (both arms).** Before any taste data is visible, the agent saves `culture-assumption.json`: its own prediction of what this audience likes in the same domains (names of works, and qualities for style, aesthetic and the qualities it expects the audience's favorite works to share), plus a `designSketch` of the site it would make from that prediction alone (3–6 colors, 1–3 library fonts, 3–8 landmark section IDs, 1–5 motifs). Both are frozen.
3. **Taste input.** `project_get_taste` then returns the Qloo profile, with each entity, tag and quality marked as predicted, named in the brief or a surprise. In Qloo off it returns the agent's own prediction. The host picks six required anchors: the strongest shared quality of each family and the three works most central to the qualities, the artifact's own medium first (games for a game site). Qloo off gets its first three predicted qualities and three predicted works. A profile without qualities gets six anchors across the entity domains, favoring surprises.
4. **Binding Design DNA.** `culture-dna.json` declares 5–10 concrete devices across at least four layers (palette and typography required). Each device is anchored to returned refs and declares literal tokens: hex colors, [library fonts](#fonts-motion-and-illustration), CSS values, keyframes, SVG illustration IDs, element IDs, copy or [library photos](#photo-library). Every required anchor is used or rejected with a reason, with at most two rejections. A device anchored to a surprise with returned tags must name the tags it translates (`qualities`). The palette and typography devices each anchor to a quality ref, a shared quality or a style or aesthetic tag, measured in Qloo on; entities are evidence of the qualities, and the prompt forbids taking an entity's own colors, logo, packaging or trade dress. A motion device translates a style ref and an SVG illustration an aesthetic ref, measured ones in Qloo on; when Qloo returned no tags for one of them, a measured mood or look quality takes its place. A [voice device](#voice-and-copy) sets the register of the copy and declares at least two lines it wrote; in Qloo on it rests on a measured ref.
5. **Departure from the sketch.** When the taste input contains surprises, the host rejects a DNA unless devices anchored to surprise entities or qualities move away from the frozen sketch. A palette device must add two colors at least CIE76 ΔE 20 from every sketch color. A typography device must use only fonts outside the sketch. A layout, structure, interaction or imagery device must add an element ID that is neither a sketch section nor a starter ID. Only Qloo on has surprises, so Qloo off may follow its own sketch.
6. **Build and conformance.** Site files can be written only after a valid DNA, and an `index.html` that changes a catalogue fact is refused. `project_check_dna` and the host check that the declared tokens appear in the saved files: colors, fonts loaded from their library files, keyframes that are defined and used, SVG illustrations with at least eight shapes, copy on the page or in the catalogue data, and for animated devices a reduced-motion fallback and, for endless loops, a pause control. The check also lists starter lines still on the page word for word. The host then measures how far the saved site moved from its own sketch, the share of its fonts, top colors and landmark sections that are new against it, and how many starter narrative lines it rewrote.

Both arms get the same model, starter and prompt except one taste-source paragraph, and neither has web or direct Qloo tools. The only difference between them is where taste comes from. Studio's TASTE panel shows what the model assumed and sketched, what Qloo measured (surprises highlighted), each DNA device with its anchors, swatches, translated tags, sketch departures and conformance, and the comparison headline. The headline counts Qloo on design devices resting on entities the model did not predict, and adds a fingerprint distance between the two sites and each site's departure from its own sketch. Taste-led plans add a model-default direction `d0` and score all four directions by measured Qloo support.

The departure is enforced by the protocol, not discovered: a Qloo on lead in departure shows that the requirement reached the saved site and that Qloo off did not drift on its own. The attribution rests on the sketches being frozen before any data in both arms. A model that sketches similar sites in both arms and then builds different ones changed course because of the taste input.

One pair is an anecdote. [`scripts/verify-taste-difference.mjs`](scripts/verify-taste-difference.mjs) runs repeated pairs and baseline-to-baseline pairs, and `--swap-from=JOB` reuses another brief's recorded profile (`tasteSourceJobId`) as a manipulation check. [`scripts/verify-qloo-taste-live.mjs`](scripts/verify-qloo-taste-live.mjs) runs only the host taste pass against the live API. Both print a plan unless given `--run`. Distance and conformance are token and structure heuristics, not measures of design quality or visitor preference. Qloo supplies entities and relationships, not design tokens; every token is labeled model interpretation. `CREATIVE_PROTOCOL=research` restores the 0.3.0 workflow below, and preparation and scoped revisions always use it.

The first live study, on October 3, 2026, ran before the sketch and departure rules. It used one Gather brief (audience: Nujabes and the film Paterson) with claude-opus-5.5. It ran three Qloo on/off pairs and three baseline-only pairs. All 12 generations completed with full DNA conformance:

- **Specification.** All 24 Qloo on DNA devices rested on entities the model had not predicted; it had predicted only 1–2 of the 69 measured entities.
- **Concept.** All three Qloo on designs became an island café with black-and-silver stationery. All nine baselines became a paper notebook, seven with a turning record. Across all 12 designs this concept split is the strongest possible in an exact permutation test (p = 0.005).
- **Rendered sites.** Palettes also differed beyond ordinary model variance (p = 0.014). Typography, page structure and CSS features did not, so the overall token distance was not significant (p = 0.21). Both arms kept the model's own serif-and-typewriter type and section plan, which is what the sketch and departure rules now address.

The same study was then repeated with the sketch and departure rules, changing nothing else. All 12 generations again completed with full DNA conformance, and each Qloo on run met the departure rule on its first DNA save:

- **Blind sketches.** Before any data, all 12 runs sketched a notebook on warm paper with a serif and a typewriter face. Their type and section plans did not differ between arms (p = 0.81 and 0.76).
- **Departure.** The Qloo on sites were 72% new against their own sketches (all of their fonts, about half of their top colors and about two thirds of their sections). The baselines were 3% new and kept every sketch font (p = 0.005).
- **Rendered sites.** Typography, structure, palette and the overall token distance now all separate beyond model variance (p = 0.005 each, the strongest possible result; typography was 0.555 and overall 0.21 in the first study). CSS features still do not (p = 0.54).
- **Look.** The Qloo on sites became a black-and-silver island almanac or night hotel set in Futura with Palatino or Gill Sans. The baselines stayed cream paper notebooks, most with a turning record.

The departure is required by the protocol, so its lead is expected. What makes the difference attributable to Qloo is that both arms started from comparable blind sketches and only the Qloo on arm then moved. It is one brief and one model, and the measures do not rate quality or preference. [`scripts/analyze-taste-difference.mjs`](scripts/analyze-taste-difference.mjs) computes the full-matrix analysis from a report. For runs with sketches, it also tests each site's departure from its own sketch and the distance between the two arms' blind sketches. When sites show library photos, it tests whether the two arms chose different photos. See the verification record for [the first study](docs/verification.md#live-taste-led-comparison--october-3-2026) and [the sketch study](docs/verification.md#live-comparison-with-frozen-sketches--october-3-2026), and the contact sheets ([first](output/taste-difference-screens/contact-sheet.png), [with sketches](output/taste-sketch-screens/contact-sheet.png)).

### Photo library

The sites in both studies had no real imagery: the preview is offline, so every picture was CSS or hand-written SVG. A starter can now carry a host photo library. `local-food` has 21 photographs of its six products, collected through [Openverse](https://openverse.org) and limited to CC0 1.0 and the Public Domain Mark 1.0, resized to at most 1280 px. [`library/local-food/library.json`](library/local-food/library.json) records each photo's creator, provider, source page and license; neither license requires attribution.

Build runs in both arms read the same catalog as `culture-library.json`: path, product, alt text, size, tone and tags that describe what each photo shows. The tags reuse words Qloo returned for this audience in the earlier runs, such as Moody, Atmospheric, Understated framing or Vibrant, so measured tags can reach the photos. A DNA device may list only catalog photos (`tokens.images`), and each must carry one of the device's qualities. In Qloo on those qualities are returned tags, so measured taste chooses the pictures; in Qloo off they are the model's own words. The same device must treat its photos with two of its own colors through a filter or blend mode, so one library can take on either arm's look. Photos show the products only; a theme such as an island or a night hotel still comes from palette, type and layout.

Previews serve only listed photos, and `project_check_dna` reports photo paths outside the library. The comparison fingerprint records which photos each site used, and a download lists the photos a site needs with their licenses. The Studio's DNA chips show the chosen photos as thumbnails.

A first live pair on October 4, 2026 used the library in both arms with full DNA conformance ([contact sheet](output/taste-library-screens/contact-sheet.png)). Qloo off chose six photos by its own qualities (soft light, overhead patterns) and put one on every catalogue card. Qloo on chose four darker photos through Moody, a tag Qloo returned for the unpredicted film Anomalisa. The two sites share one photo of nine. One pair shows the mechanism works, not an effect beyond model variance; see the [verification record](docs/verification.md#live-photo-library-trial--october-4-2026).

### Generated images

The library pictures six products, so it cannot show the island, night hotel or other theme a design takes from its taste input. When Codex is installed and signed in with ChatGPT, taste-led builds can also generate images, drawing on the ChatGPT plan rather than an API key. At startup Studio looks for a Codex CLI of version 0.160.0 or later (on Windows, the one the Codex app bundles) and checks `codex login status`. `CODEX_IMAGES=off` turns the feature off and `CODEX_CLI_PATH` selects another CLI. The service panel shows the result.

Both arms then get the same `project_generate_image` tool and prompt text, so the comparison stays symmetric. With the [production stages](#universal-production-protocol), generated images are one method a plan may choose for an imagery device: only devices whose step chose it may request pictures, up to the step's count, before any site file; a study setting can require them of both arms. With `PRODUCTION_STAGES=off`, the DNA must include an imagery device, and after saving it the agent requests one to eight images before writing any site file. For each, it names one of its imagery devices and describes in one sentence what the picture shows. The host writes the image prompt from that device: its name with taste-entity names removed, its colors (completed from the DNA palette) and its qualities, which in Qloo on are tags Qloo returned. A subject that names a taste entity or brief reference is rejected, and every prompt excludes text, logos, recognizable people and copyrighted characters. The first request freezes the DNA like the first site file. A failed request still counts, so a Codex outage cannot block a build, and `project_check_dna` lists generated images the site does not use yet.

Each image is one non-interactive Codex turn: `codex exec --ignore-user-config --ephemeral --disable shell_tool --sandbox read-only` in an empty folder, so the user's Codex configuration and MCP servers are not loaded and no host key reaches it. The host moves the image into the run's assets (as a JPEG on Windows), deletes the Codex session folder and pauses the run's deadline while it waits. Previews serve only recorded images. Each record keeps its host prompt, device and size and whether the site uses it. `culture-taste.json` carries the prompts, a download includes the images, the TASTE panel shows them with their prompts, and a scoped revision copies its source's images. [`scripts/verify-codex-image-live.mjs`](scripts/verify-codex-image-live.mjs) prints the CLI status and a sample host prompt; with `--run` it generates one real image.

A live pair on October 4, 2026 generated seven images in each arm, a hero or section image and one per product, and both sites used every one ([contact sheet](output/taste-codex-screens/contact-sheet.png)). Qloo off drew sepia ink-wash still lifes from a device anchored to its own predictions. Qloo on drew teal island-at-dusk scenes from a device anchored to the book Island, which the model had not predicted, with the returned tags Utopia and Fantasy as qualities. Both arms described the same products, some almost word for word, and the pictures still differ in medium, palette and setting. Seven images took about five minutes per arm. One pair shows the mechanism works, not an effect beyond model variance; see the [verification record](docs/verification.md#live-generated-images-pair--october-4-2026).

### Fonts, motion and illustration

A DNA could only name fonts the visitor's system happened to have. The sketch study's Qloo on sites declared Futura with Palatino or Gill Sans, so a visitor without those fonts saw a fallback. Studio now ships a font library: 33 families under the SIL Open Font License 1.1, as 57 Latin-subset WOFF2 files (1.7 MB) from [Fontsource](https://fontsource.org), each with its licence file from [google/fonts](https://github.com/google/fonts). It spans book, didone and slab serifs, geometric, humanist and grotesque sans, condensed and wide display faces, typewriter and monospace faces, a handwriting face and a formal script. Families whose licence reserves their own name are left out, because a subset or converted copy could not keep the name. [`scripts/fetch-font-library.mjs`](scripts/fetch-font-library.mjs) checks each licence before writing anything and records a checksum per file.

Both arms read the same catalog as `culture-fonts.json`: each family's category, a few words on its character, the system fonts it stands in for (Jost for Futura, Gelasio for Georgia) and the `@font-face` rules to copy. The sketch and the DNA may name only these families, and a system font is refused with its stand-in. Previews serve only listed font files, conformance checks that each declared family loads from them, and a download names the files a site needs with their licences. The TASTE panel shows each DNA font as a specimen.

Motion and illustration are DNA layers of their own. Qloo does not suggest animations, but it measures which qualities an audience's taste carries. The taste pass adds the audience's top eight style tags, ranked from film and TV, and its top eight aesthetic tags. For Nujabes and Paterson, style returned Quiet, Pensive, Visually Austere and Deadpan, and aesthetic returned Sculptural Designs, Architectural Design and Textural ([probe](docs/qloo-integration.md#style-and-aesthetic-tags)). Both arms predict style and aesthetic qualities blind, alongside their predicted works. The DNA must then include a motion device anchored to a style ref, which sets tempo, easing and what moves and declares its keyframes or transitions, and a device anchored to an aesthetic ref that draws an original inline SVG illustration with at least eight shapes. In Qloo on each must anchor to a measured tag when Qloo returned tags for its domain, and otherwise to the model's own prediction; in Qloo off both translate the qualities the model predicted. Both arms get the same construction guidance: a staggered entrance through IntersectionObserver, one signature animated moment, consistent hover and focus transitions, a reduced-motion fallback and a pause control for endless loops. The code budget rose from 25,000 to 45,000 characters to make room for them.

A live pair on October 4, 2026 ran with these rules and full DNA conformance ([contact sheet](output/taste-motion-screens/contact-sheet.png)). Qloo off kept its sketch fonts (Literata, Caveat, DM Mono) and animated its own quality "looped rhythmic structure": a record turning every 14 seconds and a 0.9-second entrance on an overshooting ease. Its SVG was a grooved record holding produce. Qloo on set Instrument Serif and Jost and anchored motion to the measured tags Quiet and Pensive, which the model had not predicted. It used a moon turning every 40 seconds, a six-second line drawing and a 1.2–1.6-second entrance staggered card by card, on an ease without overshoot. Its SVGs drew jars and bottles as sculptures on stepped plinths and a contour-plan island, from the measured tags Sculptural Designs and Architectural Design. Both sites loaded their fonts, paused with the pause button and stopped animating under reduced motion. One pair shows the mechanism works, not an effect beyond model variance; see the [verification record](docs/verification.md#live-fonts-motion-and-illustration-pair--october-4-2026).

A second live pair ran on the Echo Atlas game starter ([contact sheet](output/taste-game-screens/contact-sheet.png)). Qloo returned eight style tags and no aesthetic tags. Qloo on animated the measured tags Sweeping and Otherworldly, which the model had not predicted: skyline layers panning over 48 seconds and a seven-second ink drawing. Qloo off animated its own "slow contemplative pacing" with rings breathing on a nine-second cycle. Without aesthetic tags, both arms drew a hand-drawn city atlas. Two of the three audience references resolved to music-artist entities, because the name match dropped words such as "films" and "music"; the taste pass now reads them (step 1 above). See the [verification record](docs/verification.md#live-game-site-pair--october-4-2026).

### Voice and copy

Fonts, motion and images differed between the arms, but the words did not. In both live pairs, Gather and Echo Atlas, both arms kept all 16 of the starter's narrative lines word for word: the headline, the introduction, the section and form titles, the calls to action and every item description. Measured afterwards, 27% and 37% of the two sites' distinct sentences were identical. The prompt had told both arms to keep the catalogue data intact, and the descriptions live there.

The base structure still holds. The catalogue's facts are fixed, and the write tool refuses an `index.html` that changes them: the brand, the form's honesty notes and each item's ID, name, category, meta, price and price label, with every item in order. The narrative is now written in the DNA's voice. The headline, introduction, headings, calls to action, the add label and message, and each item description follow a voice device whose quality sets register, rhythm and vocabulary. In Qloo on that device rests on a measured entity or tag, and in Qloo off on the model's own prediction. A rewritten description keeps what the item is and does and adds no feature, award, review, quote or claim. Rewriting is not a requirement: the aim is copy that fits the taste, so a starter line may stay where it already fits. `project_check_dna` lists the starter lines still on the page, the TASTE panel shows how many each run rewrote, and the comparison counts the sentences the two sites share.

A live Echo Atlas pair on October 4, 2026 ran with these rules and full DNA conformance ([contact sheet](output/taste-voice-screens/contact-sheet.png)). Qloo off rewrote 14 of the 16 starter lines and Qloo on 13, and the two sites shared 12% of their sentences instead of 37%. What they still share is interface labels, notices and one item description that both arms rewrote the same way. Qloo off took an ambient register from its own references Brian Eno and Invisible Cities: "The city kept its sounds. Come and listen." Qloo on wrote a field log from the measured game Tacoma, which it had not predicted: "The city went quiet. Its sounds stayed behind.", with numbered log sections and a "Log this recording" button. Every product fact stayed as the starter had it. In that pass the Ambient genre tag made both tag rankings fail, so Qloo on's motion and illustration rest on its own predicted qualities; the taste pass now keeps such tag seeds out of tag rankings (step 1). See the [verification record](docs/verification.md#live-voice-pair--october-4-2026).

A second pair then ran with that fix ([contact sheet](output/taste-voice-tags-screens/contact-sheet.png)). The style ranking returned eight tags, and Qloo on animated two it had not predicted, Otherworldly and Meticulous, with a 40-second orbit and a scan line. It wrote in a question-and-answer interview voice from the measured artist Methyl Ethel and the docuseries Arnold: "Q. What is left when everyone leaves? A. The sound stays behind." Qloo off again wrote a hushed second-person voice from its own references. Qloo off rewrote 15 of the 16 starter lines and Qloo on 14, and the sites shared 10% of their sentences. See the [verification record](docs/verification.md#live-voice-pair-with-the-tag-seed-fix--october-4-2026).

### Shared qualities

Every live Qloo on design so far translated single entities literally. The ice hockey team LA Kings, tagged "Black And Silver Palette", turned a food shop black and silver; the film Anomalisa's keyword "Hotel" became a night hotel; a game engine set a game site's dark interface. The protocol made each design move, but which entity moved it depended on which one came up. The responses already held more: Qloo types every tag it returns on a work, and the profile had kept only the first eight names.

The taste pass now reads those types. Look tags (aesthetic properties, art styles, styles), mood tags (emotional tones, plots, music) and meaning tags (themes, archetypes, audiences, values, interests) are kept apart from catalogue metadata such as platforms and business models. A tag that two or more measured works carry becomes a quality, ranked by the affinity of those works and the number of domains they span. For Nujabes and Paterson, the recorded responses give Atmospheric, Minimalist and Raw (look), Reflective, Character driven and Melancholic (mood), and Identity, Love and Mortality (meaning). Three of the six required anchors are now the strongest quality of each family. The other three are the works most central to those qualities, so a work that shares none of them, such as LA Kings, is no longer required. The palette and the type must each translate a quality, with entities as its evidence. Both arms predict such qualities blind, so Qloo off follows the same rule with its own. See [Typed tags and taste qualities](docs/qloo-integration.md#typed-tags-and-taste-qualities).

A live Gather pair on October 4, 2026 ran with these rules and full DNA conformance ([contact sheet](output/taste-qualities-screens/contact-sheet.png)). Its taste pass gave the same 18 qualities and required anchors as the replay of the recorded one: Atmospheric, Reflective and Identity, then The Romantic Exiles, the Microphones and The 1st Shop of Coffee Prince, none of them predicted. Qloo on built a quiet, misty hillside pantry. Its mist-grey, fog-lilac and moss palette came from Atmospheric and Naturalistic, and Instrument Serif, Alegreya Sans and DM Mono from Reflective. Fog drifting on long loops came from the style tags Quiet and Pensive, and a sculpted terrace drawing from the aesthetic tags Sculptural and Architectural Design. LA Kings, Island and Anomalisa were still in the profile, and none anchored a device. Qloo off again made a warm paper notebook with a turning record, now from its own predicted qualities melancholic and everyday poetry. Six of the eight Qloo on devices translate measured qualities or tags; seven of the eight Qloo off devices translate qualities the model predicted. One pair shows the mechanism works, not an effect beyond model variance; see the [verification record](docs/verification.md#live-gather-pair-with-shared-qualities--october-4-2026).

## Game character

Studio's second tab, Game character, applies the taste-led protocol to one playable character in a fixed RPG scene. The world is The Long Dusk: Ilo the lamplighter walks a basalt cliff road above a sea of cloud, meets Maren, keeper of the Vesper beacon, and kindles it. The lore, the keeper, the layout, the story beats, the abilities and the engine are the same in both runs. The model writes only Ilo's character file: parts and proportions, colours and cloth, walk, idle, turn and a signature move, a light and four lines, and the moment's art direction (see [The moment](#the-moment)). Both arms get the same brief, model, prompt and design tools, except one taste-source paragraph, and neither has web or direct Qloo tools. A design server for each arm enforces the order and validates every file: prediction and sketch, the taste reveal, a Character DNA, optional Codex portraits, the character, then a conformance check.

The character uses Qloo as the websites now do, through [shared qualities](#shared-qualities). The host taste pass covers brands, film, music, books, TV and games plus the style and aesthetic rankings, makes at most 24 requests and derives the look, mood and meaning qualities from the returned works' typed tags. ### Painted characters

The data now moved every layer of the design, but the figures were still drawn the same way: rounded vector shapes on a skeleton, which the pixel frame only pixelated. A model writing coordinates cannot paint, so a pair can now paint each character as finished game art. The model still draws the rig and plans the painting; Codex paints it; the host cuts the painting back onto the rig.

1. **The plan.** Painting is a method the model's [production plan](#universal-production-protocol) may choose for one device, `painted-rig`, when the pair offers it. When the pair reviews captures, the painting comes between the review rounds: round 1 judges the vector drawing while it can still be repaired, then the model calls `game_paint_character` with a style sentence and a description of each piece, the head first: the garments, cut, materials, seams and wear that its costume and silhouette devices call for. Taste entities, tools and markup are refused. The technique comes from the render preset, so the art style that drew the frame paints the figure too: gouache for lit, oil-like concept art for cinematic, brush and wash for ink, true pixel art for pixel.
2. **The blueprint.** The host lays the drawing out as one sheet on a magenta key. The parts that share a bone and a place in the drawing order become one flat piece, split where another part covers them; each long cloth chain becomes a straight strip, and each lantern at a chain's end a piece of its own. The whole character stands on the left as the painter's reference.
3. **The painting.** One Codex edit repaints the attached sheet with the host's brief. The flat shapes are a block-in: a piece may change its outline and grow or shrink by up to a fifth, but its joints stay where they are.
4. **The cut.** The host keys out the background, gives each painted region to the piece whose blueprint it overlaps most and maps every piece onto its bind-pose box. Only a piece whose joint drifted is moved back. A painting that leaves out a body piece is refused, since the figure would have a hole; a strip or lantern that does not come back stays a vector.
5. **The engine.** The game draws the pictures on the same bones and in the same order, with the far limbs shaded. Strips bend along their simulated chains, and lanterns swing at their ends. Rig, motion, clips, cloth physics, conformance and the comparison measures are unchanged, and the painted figure takes the portrait's place on the character sheet.

Painting freezes the figure in `character.json`: its skeleton, parts, cloth, style and render, including the palette colours the parts and cloth use. The run's deadline pauses while Codex works. Round 2 then judges the painted figure. A defect it finds in the painting is repaired by a second painting of the same drawing, which the host allows only after that review. The scene, light, effects, motion, clips, lines and music stay repairable in `character.json`, since the painted pieces do not depend on them. In the first live pairs, both Qloo on arms left painting out because it froze the drawing before any review could ask for a repair, while both Qloo off arms painted. With this order and the repaint, both arms of the next pair painted, the Qloo on figure in true pixel art. That pair's open criteria were the sky, the weather and the light, which the painting then still froze. A pair with painterly references (Ori and the Blind Forest, GRIS, Okami, Spirited Away and Sigur Rós) painted both figures again: Qloo off in watercolor, and Qloo on flat, from the measured art style "minimalist" ([verification](docs/verification.md#live-character-pair-with-painterly-references--october-6-2026)). The pair publishes the pieces and the figure beside the character file. For pixel art, the blueprint is drawn on the grid the cut reads. The host reads the painting back at one picture pixel per cell, with one palette of at most 32 colours, and the game draws it without smoothing. Studio's "Making the characters" section offers "Designers may paint their character as finished game art" at up to two images per character, the second only to repair the first, and each plan decides whether to paint; "Both designers must · Paint the figure as finished game art" makes it a study setting. The command-line runner takes `--paint=1`, or `--paint=2` to allow a second edit that repairs the first, and `--require=painted-rig` for the study setting.

A spike on October 5, 2026 painted the Qloo on character of the located live pair four ways, with four Codex images of about a minute each and no Kiro or Qloo request ([contact sheet](output/painted-character-spike/contact-sheet.png)). Painting the parts freely and fitting them to the bones gave a realistic head out of scale with the body. Editing the blueprint and keeping every outline fit the rig closely, with a median overlap of 0.90 against the blueprint, but kept the vector construction. Reducing the painting to pixels afterwards gave a mosaic that lost the face, so a pixel character is painted on a pixel grid from the start. The spike's descriptions were written by hand. ## Universal production protocol

The data now reached every layer of a design, but the judgment between the data and the build was not the model's: which signals belong together, how each device is made and whether the result looks as intended. In the painted-character spike those choices were made by hand. They are now the designing model's own, in three artifacts that every host checks the same way: the Studio's websites, the game character and any project the portable plugin opens.

1. **Reading.** After the taste input and before the DNA, the designer saves a reading (`culture-reading.json`, `game-reading.json`): two to four clusters of refs that belong together, each resting on a quality (a measured one in Qloo on), the layers each should carry, the refs set aside as noise with a reason, and a paragraph on how the medium will carry the clusters. Every required anchor is clustered or set aside, at most two of them. The DNA may then anchor only to refs the reading kept, and each device to at least one clustered ref.
2. **Production plan.** After the DNA, a plan (`culture-production.json`, `game-production.json`) gives each device a method from the host's capability list for its layer: for a site a CSS palette, a library font or photos, inline SVG, CSS art, CSS motion, copy or generated images; for the character a vector or painted rig, a portrait, rig motion or a library track; for an app interface design tokens and screen layouts. A method the host cannot run is listed as unavailable with its reason, and a generator step states its count and a fallback that needs no generator. The plan also lists two to six review criteria, each concrete enough to judge met or missed in a capture.
3. **Materials as planned.** The host refuses a picture, portrait or painting for a device whose step did not choose that method, or beyond its count.
4. **Self-review.** After the conformance check, the host captures the result: a site at 1440×900 and 390×844, the character standing, walking, in the scene and kindling the beacon. The designer opens the captures with Kiro's own read tool, which the host's agent configuration points at the run's review folder (the host's own files are denied by name, and Kiro refuses any read outside the run's folder), and saves a review of each criterion: met, partly or missed, what it saw and the repair it made. There are at most two rounds; the DNA stays frozen and repairs change the build. The host reads Kiro's session record for which captures the read tool opened and records whether the files changed after each review.

Both arms of a comparison read the same capability list, so the methods each chooses are its own choice, and the comparison records them. A study setting can require a method of both arms, such as "Both designers must generate images" for a site or "Both designers must · Paint the figure as finished game art" for the character; a job that requires a method this host cannot run is refused before any request. The TASTE panel and the pair record show each reading, plan and review with its captures and the host audit. A site run gets 15 minutes by default instead of 10 and a character arm 35 minutes, and `PRODUCTION_STAGES=off` keeps the taste-led protocol for sites without the stages (`--no-production` for the command-line pair runner).

**Hosted servers.** Codex runs only on a machine where it is installed and signed in, so a hosted Studio (`MOUSA_ENVIRONMENT=hosted`, the Docker image's setting) offers no image generator: the capability list says why, plans choose methods that need none, and a study cannot require pictures. Work recorded locally with Codex pictures can be copied to the server with [`scripts/export-hosted-jobs.mjs`](scripts/export-hosted-jobs.mjs), and Studio labels those pictures as recorded with local image generation. Captures need a Chromium-based browser that can run on the server. Studio captures one test page at start and leaves the review out, with the reason, when the browser cannot run, as Chromium's sandbox cannot in a default Docker container ([deployment notes](docs/aws-deployment.md#review-captures-in-the-container)).

**Any project.** The portable plugin offers the same stages as standalone tools: `culture_list_capabilities` for a medium (`web`, `app-ui` for an interface with a design token file, or `generic` for any text project), `culture_validate_reading`, `culture_validate_production_plan`, `culture_find_materials` and `culture_fetch_materials` for its open-licence fonts, `culture_generate_image` where Codex is signed in, `culture_capture` and `culture_validate_review`. Its file tools read and write only inside `MOUSA_PROJECT_DIR`. [`examples/mobile-app`](examples/mobile-app/README.md) is a proof project outside Studio: a walking-app interface whose values live in `tokens/tokens.json`, with a Kiro CLI agent wired to the plugin.

The stages are verified with dry runs, fixtures and real Edge captures, and in live runs. In the live character pairs both arms read the taste input into clusters, planned their methods, and reviewed and repaired their characters over two audited rounds. In the first, the Qloo off arm chose to paint its figure with Codex and the Qloo on arm chose no generator; since the painting moved between the review rounds, both arms of each pair have painted ([verification](docs/verification.md#live-character-pair-with-the-production-stages--october-6-2026)). The example's own Kiro agent ran the stages once on a copy of the mobile app with the plugin alone, from its prediction to two audited review rounds ([verification](docs/verification.md#standalone-plugin-run-on-the-mobile-app-example--october-6-2026)). A live site comparison on a recorded profile ran them in both arms, with six generated pictures each and every cited capture opened ([verification](docs/verification.md#live-site-pair-with-the-production-stages--october-6-2026)). Short live Kiro sessions ([`scripts/verify-kiro-review-read-live.mjs`](scripts/verify-kiro-review-read-live.mjs)) confirmed what the review relies on: the read tool opens a capture as an image, the session record shows the read before the next tool call reaches the host, denied files are refused and reads outside the run's folder fail. Kiro does not narrow the tool to the review folder itself, which is why the hosts deny their own files by name ([verification](docs/verification.md#kiros-read-tool-in-a-review-session--october-6-2026)).

## Creative research policy — 0.3.0

The host agent identifies an open creative decision before calling Qloo. It usually explores two justified cultural domains and makes at most one focused follow-up, reusing sufficient evidence during implementation. Technical repairs, routine transformations and edits that preserve an existing direction can skip cultural research. Missing references are requested once unless the user has delegated their selection or chosen to continue without research.

The model makes the semantic assessment. The assessment tool validates the decision it declares; it is not a second model, an independent prompt classifier or a design-quality evaluator. Optional decision `queryParameters` retains relevant query choices for reassessment and reuse; actual API parameters are recorded separately with real evidence. The plugin policy also covers games, RPG work, writing and general creative tasks, while Studio's implemented production media are static websites and one playable character for a fixed RPG scene ([Game character](#game-character)). See [the policy, domain recipes and evaluation plan](docs/creative-policy.md).

## Reviewer demo

With `CREATIVE_PROTOCOL=research`, production runs record a provisional plan before any external research. Both comparison arms have Kiro's native web search and page-reading tools, with a combined six-call budget per run. Qloo on can discover cultural neighbors and investigate their concrete content; Qloo off investigates the supplied references with the same capabilities. A separate reconsideration must keep, refine or replace every tentative decision before construction. Studio displays these checkpoints, captured web excerpts and the applied output trace. This compares two complete researched workflows; it does not isolate Qloo's causal effect or establish superior design.

The host captures actual native web responses from typed tool records in Kiro's private, project-inaccessible session log. `project_get_research` exposes bounded source IDs for citation; assistant prose and agent-authored sources cannot manufacture retrieval receipts. The host synchronizes before project tools and on completion. This installed-engine adapter observes calls after invocation: order, budget or capture violations fail the generation, but it does not claim to prevent the underlying network request. Preparation has no web tools. Portable imported web records remain caller-provided and unverified. Other agent clients supply their own web tools and source collection; the plugin does not add an unseen search service. URL checks validate public-looking names and reject private address literals and capability parameters; native tooling remains responsible for DNS, redirects and network execution.

Choose a starter website and save the brief, brand protections, and audience groups. Prepare the creative brief to review the model's research decision and answer any required reference question. Preparation does not generate a website or establish that Qloo succeeded. Continue with direct generation or a comparison, or first generate creative directions, then select a direction and audience to build the website. An earlier direction plan cannot be reused after the brief or cultural context changes. A single worker processes jobs sequentially. Both sides of a comparison use independent copies of the same starter files, the same model, and the same `KIRO_EFFORT` setting (`medium` by default). The default timeout is 15 minutes per run with the production stages and 10 minutes without.

On a completed website, select a section to inspect its sources and request a scoped revision. Revision creates a new variant without modifying the source files of the existing variant. A plan or website based on Qloo evidence cannot be used as the starting point for a Qloo-disabled run. A variant's JSON export contains the context used when that variant was created; any subsequently edited workspace draft is identified separately. Imported source records are not treated as verified API calls.

A public bind requires a `DEMO_ACCESS_TOKEN` of at least 24 characters and a `PUBLIC_PREVIEW_BASE_URL` on a different origin from the application. The reviewer code is held only in browser memory. Each preview uses a temporary access URL without account credentials. Visitor pages do not place real business orders, process payments, or send invitations; the starter interactions are local demos.

## Public site and gallery

When `DATA_DIR/gallery` holds a gallery, the plain address opens Moûsa's public site and the Studio moves to `/studio`. The site has:
- a landing page with the idea and a featured comparison, the four steps of a session in that session's own data, and the three agents;
- `/gallery/`, with one page per recorded session and one per arm of a comparison.

**A session page** shows the design to play and its Taste Provenance report. It also shows what the agent did, step by step, and the commit and command that run it again.

**Security:**
- No page runs a script. A policy with `default-src 'none'` and no `script-src` serves them, and only the preview origin may be framed.
- The designs themselves are the models' own code. They play only from the preview origin, sandboxed.
- A report's files come from the app origin. A design's files never do.

[`scripts/build-gallery.mjs`](scripts/build-gallery.mjs) builds the gallery from the recorded runs [`scripts/gallery.config.json`](scripts/gallery.config.json) lists, and makes no request:

```sh
node scripts/build-gallery.mjs --runs D:/mousa-live
node scripts/build-gallery.mjs --check
```

**What each entry gets:**
- its report, and for a comparison each arm's report too;
- the report's page and card pictures, when a browser can run (`MOUSA_BROWSER` names one);
- the design's playable web files, and the starter as it was at the run's commit for a restyle;
- `entry.json`: the host and its version, the model, the Moûsa version, the time, the request and the Qloo requests. It also holds a timeline of tool names, stages and outcomes, and the command that runs the session again.

**What stays out:**
- the session streams and tool inputs and outputs;
- Moûsa's private records, including the 0.4 surface's `culture-*.json`;
- dependencies and build configuration.

**The scan.** Every text file is then scanned for local paths, the run folder, the user's name, this deployment's secrets, token-shaped strings and Qloo ids or tag URNs. With any finding, `gallery.json` is not written and the script fails. `--check` scans a built gallery again, as a deployment should before it serves one. Restart the Studio after a build.

**The blind vote** (`/vote/`) shows the two designs of one comparison from the gallery's vote pool as Left and Right, with one question such as "Which character would this audience rather play?". After the vote it says which side was made with Qloo.
- **Ballots.** A ballot is sealed with AES-GCM under a key derived from `SITE_SECRET`, so neither the page nor its picture URLs say which side is which. It expires after two hours and counts once.
- **Voters.** A vote is kept with a keyed hash of the voter's address for the day, never the address. Each address votes once a day on a pair and at most 30 times an hour. Behind a proxy, `TRUST_PROXY=1` reads `X-Forwarded-For`.
- **Results.** `/vote/results/` and `/api/vote/results` give each pair's share for the Qloo design with a 95% Wilson interval, and the limits of a self-selected vote.

A built site's root-relative URLs to its own files, such as Vite's `/assets/…`, are made relative so it plays from its gallery folder. [`scripts/verify-site.mjs`](scripts/verify-site.mjs) checks a running site. It fetches every page for its status, its policy and the absence of a script, then captures each page at 1440 and 390 pixels and each design from the preview origin.

## Showcase

A reviewer who opens the Studio sees recorded work first, without the access token: a website comparison in the Websites view, an app run in the App interface view and, once one is chosen, a character pair in the Game character view. The showcase is read-only. The server serves these records and the files they play from to anyone, while every other record, the pair list, the workspaces and every new job still need the token, and nothing in the API changes a completed record. The showcased comparison opens outside its workspace, so new work from it starts a workspace of its own; New workspace returns to the empty form, and a link to another job or pair opens that instead.

The App interface view shows the [mobile app example](examples/mobile-app/README.md) as its own Kiro agent redesigned it with the plugin alone, outside Studio: the starter and the redesign as two live phones, sandboxed on the preview origin like a site preview, then the taste pass, the reading, the Design DNA with each device's method, and both review rounds with the captures the agent judged. Studio shows the recorded files; nothing is generated again.

[`scripts/build-showcase.mjs`](scripts/build-showcase.mjs) sets the showcase in `DATA_DIR/showcase.json` and makes no request:

```sh
node scripts/build-showcase.mjs --sites=<job-id> --app=<run stamp>
node scripts/build-showcase.mjs --game=<job-id>
```

Each job must be a completed record of its kind. `--app` builds `DATA_DIR/showcase/app/<id>/` from a run of [`scripts/run-mobile-example-live.mjs`](scripts/run-mobile-example-live.mjs): the example's web files as they were, the redesign with its fonts, the captures its reviews judged and a summary of its artifacts. The copy's agent files, Kiro home and session record stay out, and the preview serves only listed web types from those folders. An entry not named keeps its value, and `none` clears one, such as `--game=none`. Restart the Studio after a change; a showcase entry that no longer names a usable record is left out with a note in the server log. With `--showcase`, [`scripts/export-hosted-jobs.mjs`](scripts/export-hosted-jobs.mjs) carries the showcase and its jobs to a hosted server ([deployment notes](docs/aws-deployment.md#recorded-local-work-on-the-hosted-server)).

## Portable plugin

### Claude Code and Codex plugins (0.6.0)

Moûsa ships as two plugins built from `plugin/`, `plugins/claude-code` and `plugins/codex`, and as a Kiro power in `plugins/kiro`. The power is in the Agent Plugins format and is installed from that folder: in the IDE through **Add Custom Power**, or with `kiro-cli powers install plugins/kiro` on the V3 engine. Each plugin carries the `mousa` MCP server, the font library, four skills and a write gate. The four skills are `taste-brief`, `design`, `compare` and `connect`. The gate holds a design's file writes between the frozen prediction and a valid Design DNA. The repository root holds a marketplace for each host:

```sh
# Claude Code
/plugin marketplace add <this repository>
/plugin install mousa@mousa
# Codex
codex plugin marketplace add <this repository>
codex plugin add mousa@mousa
```

Each person uses their own Qloo API key. They can enter it in Claude Code's plugin settings or on Moûsa's local key page, `mousa_connect`, which never passes the key through the chat. `npm run build:plugins` rebuilds the packages, and a test fails when a committed package differs from what its sources build. See the [plugin README](plugin/README.md#packages).

The plugins restyle existing projects in their own design systems: CSS custom properties, design token files and Tailwind themes. In live runs, Claude Code restyled the Ramble app (`examples/mobile-app`) through its design tokens, and Codex restyled a Vite and Tailwind CSS 4 site (`examples/tailwind-site`) through its `@theme` and its own build. Both kept every fact; see the [verification record](docs/verification.md#live-restyles-of-existing-projects--october-13-2026).

Each design ends with its **Taste Provenance** page, written by `design_report` from the session's own records. It sets the prediction the agent froze before any data beside what Qloo measured, marks each measured name new or predicted, and follows that through the reading and each DNA device to the captures the agent reviewed, with the limits. A comparison page sets the two arms side by side. The page opens from its folder with no script, and its `record.json` keeps names only: no Qloo ids, scores or descriptions. [`scripts/build-report.mjs`](scripts/build-report.mjs) writes the page for a recorded run (`npm run build:report -- <run folder>`).

The older standalone package follows.

The Moûsa plugin in `plugin/` works independently and includes a Node STDIO MCP server using the Qloo key, a manifest, and a cultural design workflow. Its technical identifier remains `culture-grounded-design` for existing client connections. The cultural brief validation and compilation tools carry Studio JSON context between agents and label imported evidence as caller-provided, unverified data. See the [plugin README](plugin/README.md) for connection details and Kiro examples.

Each client must also attach the plugin's [workflow skill](plugin/skills/culture-grounded-design/SKILL.md) to its host agent. Connecting the MCP server alone does not ensure the agent follows the policy. Studio attaches the workflow to its Kiro job. Reference selection and evidence reuse keep their declared origins; there is no shared cross-user cultural cache.

Imported research is preserved as caller-provided, unverified context. Studio keeps it in a separate `importedResearch` bundle and `culture-imported-context.json` sidecar; the operational v1 brief carries the active run's recorded sources and validated decision traces. The outer Studio export preserves the imported links without presenting them as live evidence. A bundle with missing source links is marked `complete: false`; completeness verifies links, not authenticity.

```sh
npm run pack:plugin
```

The package is created under `artifacts/`. This command does not upload it to an account or automatically install it in a client.
