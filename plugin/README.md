# Moûsa — portable plugin

Moûsa brings cultural context to creative agents. This folder is its self-contained local plugin. It requires Node.js 22 or newer and has no npm dependencies. The app imports this same implementation through `src/qloo/client.mjs` and `src/mcp/server.mjs`. The technical identifier `culture-grounded-design` is retained for existing MCP connections and skill paths.

The global hackathon workflow requires English for generated interfaces, design artifacts, creative directions, decision notes, and user-facing exports, regardless of the conversation language.

Standalone mode provides six culture tools (`culture_assess_decision`, `culture_validate_brief`, `culture_compile_brief`, `culture_validate_design_dna`, `culture_check_dna_conformance`, `culture_compare_designs`), eight production tools (see [Production stages](#production-stages)) and five Qloo tools. The culture tools work without an API key. Qloo tools resolve cultural entities and tags, retrieve insights, compare separate taste queries and build a bounded taste profile using documented GET `/search`, `/v2/tags` and `/v2/insights` endpoints. Name resolution is separate from taste inference. Qloo returns aggregate cultural affinities, not a new graph, individual preferences, or correctness scores for generated designs.

Successful standalone Qloo replies receive an `evidence.id` beginning with `culture-source:` and `evidence.idKind: "application-source-record"`. This identifier is generated by the plugin for a source record; it is not a Qloo cultural entity ID or a provider-issued identifier. Cite it in portable research records, retaining the returned endpoint and original retrieval time. Each successful comparison group receives its own identifier; errors create no source record. Studio and other hosts with an `onEvidence` callback retain ownership of their source IDs. Imported records still remain caller-provided and unverified.

Set `QLOO_API_KEY` in the MCP process environment or the host's secret environment facility. The default base URL is `https://hackathon.api.qloo.com`. Do not put a credential into this plugin, client configuration examples, artifacts, browser code, or logs. Without a key, tool discovery works and a Qloo tool returns an explicit `QLOO_KEY_MISSING` error. Set `QLOO_BASE_URL` only when using a credential issued for another documented Qloo environment.

## Portable configuration

`mcp.json` uses `${PLUGIN_ROOT}` for plugin-aware clients. For Kiro or another generic stdio MCP client, use its supported MCP configuration location and substitute the absolute extracted plugin path:

```json
{
  "mcpServers": {
    "culture-grounded-design": {
      "command": "node",
      "args": ["D:/Qloo Hackathon/plugin/server/index.mjs"]
    }
  }
}
```

This is a configuration example, not an installation or evidence that a Kiro connection was made. Restart or reconnect the client, initialize, list tools, and make a harmless lookup after configuring the key.

Attach `skills/culture-grounded-design/SKILL.md` to the host agent's instructions or supported skill mechanism as well as connecting MCP. Tool discovery alone does not attach the decision policy. The agent semantically identifies an open creative choice; `culture_assess_decision({decision,context,previousResearch?})` validates the declared context and returns `research`, `reuse`, `clarify` or `skip` without a network call. Audience references, creator inspiration, brand references and world canon have distinct roles; selected origins remain user-provided, existing-context or agent-selected. Technical repairs and routine transformations can skip research. A creative task without references asks once unless selection is delegated or research is declined.

## Taste-led design (0.4.0)

When measured taste should govern a design, follow `skills/culture-grounded-design/taste-policy.md`. The portable sequence is:

1. Write your own prediction first: `{schemaVersion:'1.0', audienceSummary, predictions:{brand:[…], movie:[…], …, style:[…], aesthetic:[…], qualities:[…]}, designSketch?}` with three to six real names per entity domain and three to six qualities (single words or short phrases) for `style`, `aesthetic` and `qualities`, the last being moods, themes or looks you expect the audience's favorite works to share. The optional `designSketch` `{summary, palette, fonts, sections, motifs}` is the design you would make from the prediction alone: 3–6 hex colors, 1–3 font families, 3–8 landmark element IDs and 1–5 motifs. Keep it as written.
2. Call `qloo_taste_profile({references, domains?, location?, assumption, knownNames?})`. It resolves the references (entity search, then tag search, strict name matching; a same-named work wins over a place). A reference's last category word limits what may seed it: "Studio Ghibli films" accepts only films or their makers, and "ambient music" asks for a music genre tag before any artist. It then requests cross-domain neighbors that exclude the seeds, two at a time, adds a lower-popularity band for brands and film, ranks the audience's style tags (film and TV parents) and aesthetic tags, and stops at 24 requests. The `qualities` domain costs no request: it groups the typed tags of the returned works into look, mood and meaning, leaves out catalogue metadata such as platforms, and keeps each tag two or more works carry as a quality ref (`quality:look:atmospheric`) with its count, domains and examples. The default domains are brand, movie, artist, book, tv_show, style, aesthetic and qualities. With `assumption` it returns `tasteInput`: every measured entity, tag and quality marked as predicted, named in the brief or a surprise, plus your own predictions and six required anchors. With qualities these are the strongest quality of each family and the three works most central to them; otherwise they are drawn from the entity domains. The prediction is validated before any request.
3. Compile a Design DNA of 5–10 concrete devices and validate it with `culture_validate_design_dna({dna, tasteInput, sketch?, existingIds?, library?})`. Palette and typography devices are required; each device cites refs from `tasteInput` and declares literal tokens. Every required anchor is used or rejected with a reason. A device anchored to a surprise with returned tags names the tags it translates in `qualities`. With your `sketch` and surprises in `tasteInput`, the DNA must also depart from the sketch. A surprise-anchored palette device needs two colors at least CIE76 ΔE 20 from every sketch color, and a typography device only fonts outside it. A layout, structure, interaction or imagery device needs an element ID outside both the sketch and `existingIds` (the IDs already in your starter). If your host has a photo library, pass it as `library: [{path:'library/<id>.jpg', tags:[…]}]`. A device may then list only those photos in `tokens.images`, each sharing a tag with the device's `qualities`, and must treat them with two of its colors and a `filter` or `mix-blend-mode` value. When `tasteInput` has style refs, include a `motion` device anchored to one, with `tokens.keyframes` or an animation or transition CSS value; when it has aesthetic refs, include a device anchored to one that lists the IDs of its inline `<svg>` illustrations in `tokens.svg`. Each must use a measured ref when the profile returned tags for its domain; when it returned none but has measured qualities, motion anchors to a mood quality and illustration to a look quality. When `tasteInput` has qualities, the palette and typography devices each anchor to a quality ref (a quality, style or aesthetic ref), a measured one when it has measured qualities; entities are evidence of the qualities, never a source of their own colors, logos or trade dress. Every DNA also needs a `voice` device that sets the register of the narrative copy and declares at least two lines it wrote in `tokens.copy`, anchored to a measured ref when `tasteInput` has measured entities. Conformance finds a copy line on the page or in a JSON data island the page's script renders. If your host serves fonts, pass them as `fonts: [{family, files:['fonts/<file>.woff2'], similarTo?:[…]}]`; typography may then name only those families, and a system font is refused with the family that stands in for it.
4. Build the artifact, then call `culture_check_dna_conformance({dna, files, library?, fonts?})` and repair missing devices. It checks keyframes that are defined and used, SVG illustrations with at least eight shapes, and for animated devices a `prefers-reduced-motion` fallback and, for endless loops, a `data-motion-toggle` pause control. With `library` it also lists referenced photo paths the library does not contain; with `fonts` it checks that each declared family is loaded from its files with `@font-face`. `culture_compare_designs({a, b})` returns a bounded fingerprint distance between two static designs.

Unresolved references, empty domains and failed requests are reported, never filled in. Conformance shows that tokens exist in the files; distance shows that two token systems differ. Neither measures quality or preference, and one comparison does not separate data from ordinary model variance.

## Production stages

The production stages add the designer's own judgment between the taste input and the build, as artifacts the tools check: a reading of the taste input, a plan of how each DNA device is made from the methods this machine offers, and a review of captures of the result. Read `skills/culture-grounded-design/production-policy.md`, the same text Studio and the game host give their agents. In a standalone session:

1. `culture_list_capabilities({medium})` lists what this session can make for the medium: `web` (a website), `app-ui` (screens whose values live in a design token file such as `tokens/tokens.json`, consumed through CSS custom properties) or `generic` (any text project, checked by finding each token as written). It names each method per DNA layer and the reason any is unavailable, and the views a capture shows: desktop 1440×900 and mobile 390×844 for `web`, phone 390×844 and board 1440×900 for `app-ui`.
2. After the taste input, `culture_validate_reading({reading, tasteInput, medium})` checks the clusters, the set-aside refs and the required anchors. Pass the valid reading to `culture_validate_design_dna`, with `medium`.
3. `culture_validate_production_plan({plan, dna, reading, tasteInput, medium})` checks that each step's method is available here and makes the device's layer, that generator steps have a count and a fallback, and that every cluster is realized.
4. `culture_find_materials({kind:'fonts', words})` ranks the 33 open-licence (SIL OFL 1.1) families the plugin carries; `culture_fetch_materials({fonts, plan})` copies the planned ones into the project with their licence files and returns their `@font-face` rules. `culture_generate_image({dna, device, subject, plan})` makes one picture for a planned imagery device where Codex is installed and signed in, up to `MOUSA_IMAGES_PER_RUN` (4 by default, at most 8) per session.
5. After `culture_check_dna_conformance({dna, paths, medium})`, `culture_capture({medium, views?, target?, full?})` renders a project page in a headless Chromium-based browser that can reach only the project, and `culture_validate_review({review, plan})` checks a review against the captures this session issued: two rounds of at most six captures. Open every capture you cite with your own image-reading tool; this session cannot confirm which ones you opened, and the reply says so.

The server's environment configures the session; a tool never takes a folder from the agent:

| Variable | Effect |
| --- | --- |
| `MOUSA_PROJECT_DIR` | The project folder. The file tools work only when it is set and read only inside it; they write only the fonts and pictures they fetch or generate, and the session's captures and records under `.mousa/` |
| `MOUSA_LIBRARY_ROOT` | The folder that holds `library/fonts`; by default the plugin's own folder, then the repository it sits in |
| `MOUSA_ENVIRONMENT` | `hosted` lists no image generator, whatever is installed |
| `CODEX_IMAGES`, `CODEX_CLI_PATH` | `off` turns image generation off; the path selects another Codex CLI |
| `MOUSA_CAPTURE`, `MOUSA_BROWSER` | `off` turns captures off; the browser path selects another executable |
| `MOUSA_CAPTURE_NO_SANDBOX` | `1` runs the browser without its own sandbox, for a container that blocks it; the container is then the only boundary around the captured pages |

A browser counts as available only once it has captured a test page in this process, so a machine where it cannot run lists the review as unavailable with the reason. In the Moûsa repository, `examples/mobile-app` is a proof project with a Kiro CLI agent wired to this server.

## Portable authored context

`culture_validate_brief({brief})` checks bounded JSON and references; `culture_compile_brief({brief})` returns portable context with separate evidence and creative-decision records. Neither tool calls APIs, accesses files, verifies an audience, or authenticates imported records. They are available in standalone, bridge, and baseline sessions.

An authored brief can start with product context alone:

```json
{
  "schemaVersion": "1.0",
  "product": {
    "name": "My product",
    "templateId": "landing-page",
    "brief": "Describe the concrete user job and production requirements."
  },
  "audiences": [],
  "evidence": [],
  "decisions": []
}
```

Optional fields include `brand`, `selectedDirection`, `constraints`, typed `creativeContext` and `researchDecisions`. Audience records need unique `id` and `label`; evidence needs unique `id` or `evidence.id`. Decisions may link `evidenceIds` and `audienceIds`, which must exist in the same brief. Limits are 8 audience groups, 100 evidence records, 80 decisions, 4000 characters per text field (8000 for a literal `brand.protectedSnippets[].text`), nesting depth 16, 1500 JSON nodes, and 64 KiB total UTF-8. Secret fields, prototype fields, unsupported schema versions, and dangling references are rejected.

Actual Studio artifact metadata is also accepted and preserved: `audienceId` (at most 100 characters, referencing an existing group), `revisionRequest` (at most 4000 characters), and `provenance` (at most 200 characters). The context's original provenance text remains an imported caller claim. The compilation envelope and each evidence wrapper still label the source as caller-provided and unverified, including records claiming `studio-recorded-qloo-responses`.

Compilation returns `schemaVersion: "1.0"`, `provenance: "caller-provided-unverified"`, and `context`. Imported evidence is wrapped as `{id, verification: "caller-provided-unverified", record}`. Creative decisions are wrapped as `{kind: "creative-interpretation", record}`. A caller can claim a record is verified inside its original data; this tool still does not authenticate it. An application that actually made a Qloo call must maintain its own source audit separately.

For a Studio export or previous compilation, pass `culture_compile_brief({brief: exported.context})`. Both raw Studio records and the compiler's labeled wrappers are accepted. Recompiling normalizes recognized wrappers to one layer, preserves their original data, and revalidates the original creative decision's links. Wrapper IDs must agree with their original record IDs; unsupported wrapper fields are rejected rather than discarded. The outer Studio snapshot provenance is not promoted to verified Qloo provenance by importing its context.

## Explainability and taste comparison

`qloo_get_insights` accepts optional `explainability: true`, sent as GET `feature.explainability=true`. If Qloo returns it, the tool preserves bounded, sanitized metadata in each result's `explainability` and the top-level `explainability`. These copy the API's corresponding `query.explainability` objects, including a returned warning. Inner field names are not invented or normalized to an assumed schema. Copies are limited to depth 6, 300 JSON nodes, 50 array items, 40 object fields, and 1000 characters per text; omitted data is not replaced with invented scores. Missing explainability remains missing.

The official reference describes normalized seed contribution values, not probabilities. This supports the trace `authored design decision → returned cultural anchor → returned seed contribution`. The link from a cultural anchor to CSS, typography, layout, or copy remains the designer's creative interpretation. The public documentation does not provide a detailed response schema for the nested explainability object; live shapes and feature availability must be observed, not assumed.

The live hackathon diagnostic returned both per-entity and aggregate explainability for its artist, brand and artist-shortlist requests. Optional bounded `responseQuery` and `warnings` preserve the upstream query context and warning data when present. This can retain actual locality-resolution metadata without assuming a field exists; missing metadata remains missing. These sanitized copies use the same bounded metadata rules, rather than passing arbitrary upstream instructions or credentials to the host.

`qloo_compare_tastes({groups, resultType, location?, limit?, explainability?, tagTypes?, parentTypes?})` accepts 2–3 groups, each `{id, label, seedEntityIds}`. It issues one independent insights request per group in parallel and retains each query's source and original affinity. `sharedCandidates` contains only entity IDs found in every returned list, with separate group support records; no compatibility or design score is calculated. This is an intersection of bounded result lists, not a verified intersection of human audiences. An empty intersection does not prove there is no common taste.

Every successful comparison query is passed to `onEvidence` as `qloo_get_insights`, with `comparisonGroupId`; the application comparison itself is not an extra Qloo source record. If any query or host audit fails, the tool returns an error with `QLOO_COMPARISON_INCOMPLETE`, successful query data, failed group errors, and `comparisonComplete: false`. An audit failure is labeled `QLOO_EVIDENCE_AUDIT_FAILED`; other successful queries are still passed to the callback. No intersection is claimed. A host with an API-call budget must count every group request, not just the single comparison tool invocation.

For `resultType: 'tag'`, optional `tagTypes` maps to `filter.tag.types` and `parentTypes` maps to `filter.parents.types`. Both accept at most four entries and are rejected for non-tag result types. A documented media-tag recipe uses `tagTypes: ['urn:tag:keyword:media']` and `parentTypes: ['movie', 'tv_show']` with original resolved seed IDs. A live request using the Paterson seed returned six tags consistent with that namespace and returned parent metadata; it returned no explainability metadata. This is observed delivery and consistency, not a promise about other seeds or proof of a counterfactual filtering effect. Unknown or inapplicable upstream parameters can be silently ignored, so a successful status alone does not prove a filter was applied. A live style-tag request with an entity seed returned eight tags, and the same request with a genre tag seed added returned HTTP 500, so the taste pass leaves tag seeds out of tag rankings when an entity seed exists.

## Active design job bridge

The app can launch the same entrypoint with `CULTURE_BRIDGE_URL` (loopback HTTP or HTTPS) and `CULTURE_BRIDGE_TOKEN`. In this mode, calls are forwarded as `{ "name": "...", "arguments": {} }` to POST `/internal/tools` with a bearer token. The backend binds that token to one active job and handles authentication and file scope. The MCP process has no direct project filesystem access.

Bridge mode also lists `project_list_files`, `project_read_file`, and `project_write_file`. Standalone mode exposes the culture assessment/brief tools and Qloo tools. Tokens and Qloo keys are not returned by these tools.

With `CULTURE_PROTOCOL=taste`, a bridge session lists `project_get_taste` and `project_check_dna` instead of `project_get_research`, and omits the portable DNA tools and `qloo_taste_profile`: the host owns the taste pass, the prediction gate and conformance. `project_get_taste` returns only the prediction domains until `culture-assumption.json` is saved.

When the host can generate images, it also sets `CULTURE_IMAGE_TOOL=true` and the taste bridge lists `project_generate_image({device, subject, aspect?})`. The agent names an imagery device of its saved DNA and describes what the picture shows; the host writes the prompt from that device's name, colors and qualities, rejects subjects that name taste entities, and returns a local `generated/<name>.jpg` path. Studio then requires an imagery device in the DNA and at least one image request before the first site file. The bridge waits up to 270 seconds for this tool and 25 seconds for every other tool.

Set `CULTURE_ENABLE_QLOO=false` for a baseline bridge session. All Qloo tools, including comparison, are then absent from discovery and rejected if called directly. The baseline retains the portable brief tools, the same project tools, and artifact limits. Standalone mode always exposes Qloo tools, since it has no project job to compare.

Application limits: 20 seed IDs, 10 tag seeds, 50 optional shortlist IDs, 50 excluded IDs, 20 returned results per call, 24 requests per taste profile, 15-second Qloo timeout, and 128 KiB per file write. These are our caps, not vendor quotas. Qloo's official Insights maximum is 50 returned results; Search's documented `take` is below 200. No numeric hackathon rate quota is specified in the guide. A live taste pass with four parallel requests hit the rate limit on three of seven insights calls. The taste pass therefore retries a request that hits a rate limit, a timeout, a network error or a server error at most twice, records every attempt and counts each one toward its 24-request budget. Its style and aesthetic rankings use the entity seeds alone whenever an entity resolved, because a genre tag seed beside them returned server errors, and an entity request with both kinds of seed that times out or gets a server error twice is sent once more with the entity seeds alone. No other request is retried automatically. Affinities are preserved as returned, never converted into percentages.

The optional insights `location` conditions geographic taste with `signal.location.query` for a locality name, or `signal.location` for WKT geometry or a resolved locality UUID. It does not restrict results to places physically inside that area. Qloo's `filter.location` has that different purpose and is limited to Place/Destination results. The general parameter reference documents location signals across the supported entity categories, and the taste-analysis reference also documents them for tags. A location is context for aggregate evidence, not a demographic label or proof of an individual's preferences. Recognition of a locality and regional coverage require a successful live response.

Search uses a separate category list, including legacy lookup categories actor, album, author, director and locality. These are not additional Insights result categories. Search's returned `types` array is preserved and used when no `type` or `subtype` is returned.

The official API reference uses `videogame` in the current game schema; the hackathon guide also contains a conflicting `video_game` spelling. A real hackathon request confirmed `urn:entity:videogame` with HTTP 200 and returned game entities, while `urn:entity:video_game` returned HTTP 400. The implementation therefore keeps canonical `videogame`. A specific game or regional entity's coverage is verified only by a successful live response.

## Observed live coverage

The October 3, 2026 local-time API diagnostic made eight real requests and no model calls: Search for Nujabes, Paterson and Muji; six-result artist and brand insights; a three-entity artist shortlist; and both conflicting game spellings. It verified the selected lookup/insights paths and real explanation metadata. The failed underscore probe remains a rejected request, not evidence.

A separate four-call diagnostic initialized and discovered the actual HTTP and standalone STDIO MCP servers and retrieved real sources through both transports. The fresh STDIO handler assigned an application-owned source-record ID; the HTTP server used its previously loaded handler without that new ID. It also returned six media tags and recognized Tokyo under actual `responseQuery.localities.signal` metadata. These observed mechanics do not establish a full agent workflow, geographic ranking influence, multi-group coverage, a completed Kiro/Qloo website or design improvement. In the repository, see `docs/qloo-integration.md` and the recorded live reports for scope; standalone users should verify their own credential and account coverage.

A later actual Opus 5.5 Studio comparison completed a baseline and Qloo website from equal prepared inputs and independent starter copies. Baseline made no source calls; Qloo made four calls for two original reference lookups and tag/movie insights. Five validated research traces linked observations and creative interpretation to the output, with three design decisions citing usable insights. Protected runtime equality and actual output targets passed. The first attempt's invalid creative-record artifacts remain documented; immediate write validation now lets the agent correct those records. This establishes the selected Studio production path, not superior design quality, general domain outcomes or another host's workflow.

The saved comparison also passed browser checks for both outputs at 375/1440 pixels: original product facts, search/filter/sort, selection, embedded local forms, English presentation, source links and downloads. No new generation/API calls were made by that verification. The final latest-work export remained consistent after server restart. The repository verification record contains the observed scope and corrected preview/export defects.
